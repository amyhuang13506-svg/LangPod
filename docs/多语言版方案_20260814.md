# Castlingo 多语言版实施方案（韩语先行，5 语言全预留）

## Context

现状是纯中文版：UI 中文硬编码（~800 处，0 处本地化）、内容翻译层中文（`*_zh` 字段焊死在 OSS schema / App 模型 / pipeline prompt 里）。目标：上线多语言版——非中文母语用户学英语，**英语原声内容全复用**（英语音频+时间戳、封面、课程图片、课程/表达英语音频），只新增各语言"翻译层"。

已确认的决策：
- **5 语言全预留，韩语先行试点**：ko / ja / zh-Hant / es / pt-BR 架构一次注册到位；韩语先跑 2 周校准 AI 质检系统，跑通后其余 4 门并行开闸（获客渠道已成熟，无需按市场分波）
- **全模块**：核心播客 + 句型讲解 + 情景课/表达库 + 原声播客（es/pt 首发可视质检情况后置 patterns）
- **UI 语言和翻译语言都跟随系统语言**，无手动切换
- **中文版零回归**：线上老版本还在用现有 OSS 路径/schema，中文文件一个字节不动
- **质检靠 AI**：四层质检漏斗 + 自动修复回路（见"AI 质检系统"节），人工只做每语言一次性 $30-50 的母语者校准
- **繁中特殊通道**：翻译音频直接复用普通话音频，文本 OpenCC 简转繁 + GPT 润色用词，边际成本 1-2 天

## 总体架构

1. **新语言 = sidecar 文件**：与原文件同目录，文件名加 `_ko` 后缀（`index_ko.json` / `episode_ko.json` / `ko.mp3` / `transcript_ko.json`…）。中文 legacy 文件不动。
2. **新文件用语言无关字段名**，App 做集中式双 key 解码（generic 优先，legacy `_zh` fallback）。
3. **生成侧解耦**：中文流程原样不动；新增"本地化 pass"从定稿的 `episode.json` 派生 `episode_ko.json`（英文原文翻译，非中文转译），每日增量与存量回填走同一套代码。
4. **失败隔离**：韩语层独立 cron + 队列 + 独立日志，失败不影响中文发布。

## 一、Pipeline / 服务器（/opt/langpod/pipeline，本地 pipeline/）

### OSS 布局（新增文件）

```

episodes/{level}/index_ko.json          # 只收录已有 episode_ko.json 的集

raw_podcasts/{id}/words_ko.json         # EN→KO 点查词典
```

英语骨架复用：episode_ko.json 的 `text/example/start/end/audio.english/thumbnail` 逐字段拷贝自 episode.json；pattern 的 template/例句英文/六段结构复用 zh 版（各语言用户学同一批 pattern），只重写母语讲解 + 重合成音频；lessons/expressions 的图片和英语音频 URL 照抄（**只需文本翻译，无音频成本**）。

### 改动文件（zh 路径字节级不变）

- `generate_audio.py`：L245-274 中文逐句合成抽成 `synthesize_translation_track(lines, voices, out, provider)`，zh 调用参数=现值
- `transcribe.py`：`_translate_one_batch`(L298) 加 lang 参数，prompt 从 prompts 模块取，zh 默认=现 prompt 原文
- `pretranslate_words.py`：加 `--lang`，输出 `words_{lang}.json`
- `upload_oss.py`：新增 `upload_localized_episode()` + `update_episode_list(bucket, level, lang)`（遍历 episode_ko.json 重建 index_ko）
- `generate_daily.py` / `raw_podcast_processor.py`：产物上传成功后 enqueue localize（try/except 非致命，各 ~5 行）
- `push_new_episode.py` / `push_new_raw_podcast.py`：targets 按 token 的 `language` 字段分组（devices_server.py 已存该字段，默认 zh），每组用 `LANGUAGES[lang]` 文案；queue schema 不用改（title 是英文，共用）

### 韩语 TTS 选型（P0 先验证）

首选 MiniMax speech-02-hd 韩语 voice（**待试听验证**，用 audition 脚本对翻译男/女声 + pattern 讲解声三个角色出样本）；备选 ElevenLabs multilingual（pipeline 已有集成；讲解音频可 ko+en 同一 voice，拼接更自然）。验收：韩语自然度、英文夹读、数字朗读。

### 韩语内容规则移植要点

- 错误发音示范："Konglish"한글转写（coffee→커피 式 f→ㅍ、th→ㅆ、词尾加 으/우），机制对应中文版的"英文+句号断开"
- 字幕切分：句末 `.!?…`、次级逗号、最后按**空格（词边界）**切（韩语有空格，优于按字符硬切）
- lessons/expressions 的 `culture_tips`/`usage` 里"中文母语者视角"的对比内容让 GPT 重写为韩语视角，非直译

### AI 质检系统（pipeline/qc/ 模块）

四层漏斗，每层通过才进下一层；语言无关，按 `languages.py` 的规则参数化：

| 层 | 文件 | 内容 | 成本 |
|---|---|---|---|
| L0 机械规则 | `qc/rules.py` | 目标语言字符占比 ≥60%、**出现汉字即拒（防中文串漏）**、字幕长度、六段完整、行数对齐、占位符完整、音频存在/时长 | 免费 |
| L1 LLM Judge 全量判卷 | `qc/judge.py` | 英文原文+译文逐行判 `{行号,分数1-5,问题类型,修改建议}`（准确/母语自然度/语域/术语）；patterns 按 10 条规则改写成的机器可判断言逐条打勾；**判卷换模型**（不与生成同系列）+ 母语者 persona、prompt 用目标语言写；低分行触发回译比对二次确认 | ~$0.02/集 |
| L2 音频 ASR 回环 | `qc/asr_check.py` | TTS 音频 → whisper 强制目标语言转写 → 与源文本算 CER，超阈值=TTS 读错/漏读/artifact（复用 transcribe.py 的 whisper 设施）；外加时长/静音占比/削波检测（复用 trim_tts_tail 能量检测逻辑） | whisper 本地免费 |
| L3 抽样深审 | `qc/panel.py` | 每日抽 10% 过三 judge 投票（不同 prompt/模型），分歧进隔离区 | ~$0.5/天 |

**修复回路（`qc/repair.py`）**：失败行/段带 judge 批语重新生成（最多 2 次）→ 仍失败进隔离区不上传（该 pattern 跳过，播客本体照常发布）→ 每日 `qc_report_{date}.json` + 失败率异常 APNs 告警到开发机（复用 check_push_health.py 模式）。

**一次性人工校准（`qc/calibrate.py`）**：每语言 Fiverr/Upwork 找母语者评 30 条校准集（~$30-50/语言），对齐 judge 阈值；这 30 条固化为 **golden set**，每次改 prompt 重跑防质检标准漂移。此后零持续人工。

5 语言全开质检总成本约 **$1-2/天**。

### Cron 编排

```
0 3   generate_daily.py            # zh 原样，末尾入 localize 队列
30 4  localize_daily.py            # 各语言层生成+QC+上传+重建 index_{lang}
0 6   localize_daily.py --retry    # 失败补跑，>72h 过期告警
30 7 / 0 17  flush_pending_pushes  # 不变（push 脚本内部按 language 分组）
```

## 二、iOS App（LangPod/）

### 语言抽象层（新建 `Models/ContentLanguage.swift`）

`enum ContentLanguage { case zh, zhHant, ko, ja, es, ptBR }`（5 门一次写全，未上线语言在 resolve 里暂不返回即可），启动时扫**完整** `Locale.preferredLanguages` 解析一次（命中 zh/ko；英文手机的韩国用户 preferred 列表里通常有 ko）；其他语言 fallback **zh**（翻译音轨是 5 遍流程第 4 遍，无"无翻译模式"；zh 内容目录最全）。`fileSuffix`：zh→`""`、ko→`"_ko"`（缓存后缀同规则，zh 老缓存文件名不变，免迁移）。UI 语言不用代码判断——String Catalog 自带 fallback 链（非 zh/ko 系统落 en）。

### 模型解码（集中式，不逐个手写 init）

- 新建 `JSONDecoder.castlingo()`：`keyDecodingStrategy: .custom` 用上面的映射表把 legacy `_zh` key 改写成 generic key → zh 老文件（含老磁盘缓存）和 ko 新文件命中同一套 CodingKeys。APIService / MockDataLoader / 缓存读取统一换用。
- **属性 rename 单独一个零逻辑 PR**：`translationZh→translation`、`exampleZh→exampleTranslation`、`textZh→textTranslation`、`nameZh→nameTranslation` 等（Xcode Rename，纯机械）。
- 持久化模型（SavedWord 手写 init L105-119、ListenedPattern）走 UserDefaults 裸 decoder，用 container helper `decodeString(_:legacy:)` 双 key 兼容老数据，encode 写新 key；**SavedWord 加 `language: String?` 字段**（decodeIfPresent ?? "zh"）。换系统语言后老快照按原样显示（V1 不迁移不隐藏）。
- `VocabularyStore.migrateExampleTranslations()` 加 `guard ContentLanguage.current == .zh`（防 bundle 中文回填污染 ko 快照）。
- `LessonStore` L288-301 分组 key 从 `categoryZh` 换成语言无关 `category` slug（正确性修复，必做）。

### APIService

- 9 个端点统一走 `contentURL(dir:file:)` builder，文件名拼 `lang.fileSuffix`
- 9 处重复的缓存目录构建收敛成一个属性 + `cacheFileURL(_:)`；缓存文件名加 `lang.cacheSuffix`；**缓存目录加版本段**（`CastlingoEpisodes/v2/`），未来 schema 演进直接 bump 版本，不再靠 decoder 兼容老缓存
- **契约测试**：pipeline 生成的各语言样例 JSON 作为 fixture 提交进 App 仓库，单测断言完整解码——防 iOS 与 pipeline 字段映射漂移（替代跨语言共享配置的重方案）
- ko 文件 404 保持现有"空 → bundle fallback"链路，**不做跨语言回落**（给韩国用户看中文比看种子数据更糟）

### UI 本地化（~800 处）

**核心决策：开发语言保持 zh-Hans，中文字面量即 key** → View 层 `Text("首页")` 建 String Catalog 后零代码改动、编译期自动抽取；zh 显示即 key 原文，零回归有结构性保证。
- 新建 `Localizable.xcstrings`（ko/ja/zh-Hant/es/pt-BR/en 六个 locale 一次建全，未上线的暂不填）+ `InfoPlist.xcstrings`（权限文案）；pbxproj `knownRegions` 补全
- **占位符校验脚本**：检查 xcstrings 各语言译文的 `%@`/`%lld` 占位符与源文一致（LLM 翻译常弄丢占位符），进 CI/提交前检查
- 批 A：View 层字面量（catalog 自动抽取，处理歧义 key 和 `+` 拼接串）
- 批 B：非 View 层手动包 `String(localized:)` ~150-200 处：Model computed 属性（PodcastLevel.tabName、MemoryState/MasteryLevel.label、PatternSection.label、PlaybackPhase.label、LearningGoal 全套…）、SubscriptionManager(46)、NotificationManager(13)、AudioPlayer 锁屏文案、TaskEngine
- 批 C：格式化——`Episode.dateDisplay` "M月d日" 改 `.formatted(.dateTime.month().day())`，durationDisplay 走 format key
- ko 翻译 LLM 初翻 + 审校；en 是 fallback 标准可略低；韩语文本普遍比中文长 20-40%，逐页查溢出

## 五语言展开（韩语试点跑通后）

韩语 2 周试点校准的是**质检系统本身**（judge 阈值、修复回路、golden set 流程），跑通后其余语言并行开：
- **zh-Hant**：1-2 天（OpenCC 转换 + 润色 prompt + UI 繁化 + 音频复用），最先上
- **ja**：prompt 移植比韩语快一半（カタカナ英语对应 Konglish 机制），TTS 试听 + 校准集 + 回填
- **es / pt-BR**：同流程；patterns 讲解视 judge 校准结果决定首发带不带
- 每门新语言固定动作：languages.py 填 voice/规则 → prompts_{lang}.py → $30-50 母语者校准 30 条 → xcstrings 翻译 → 回填 → ASC 商店材料

## 工作量与成本

- 工时：韩语试点约 **3-4 周**（P2/P3 与 P1/P4 并行可压缩）+ AI 质检系统约 3-5 天；其余 4 语言并行展开约 1.5-2 周
- 一次性内容回填：每语言 **$150-300**（zh-Hant 除外，接近 $0），5 语言合计约 $600-1200 + 校准 $150-250
- 每日新增：每语言 $2-3（GPT + TTS）+ 质检 $1-2/天，5 语言全开约 **$12-17/天**
- 质量保障：AI 四层质检 + 每语言一次性母语者校准，零持续人工

## 关键风险

1. TTS 各语言 voice 质量未验证 → 每语言 P0 试听（audition 脚本复用），备选 ElevenLabs multilingual
2. LLM judge 判卷不可靠（自我偏袒/标准漂移）→ 换模型判卷 + 每语言 30 条母语者校准 + golden set 回归；judge 与人评对不齐的语言，patterns 后置上线
3. 中文版回归 → 三重保险：zh 文件不动 + zh 缓存/存储 key 不变 + fixture 单测 + zh 流程 diff 验证
4. 5 语言全开后固定成本 ~$400-500/月 → 按语言看 DAU/订阅数据，转化不动的语言可停 daily 生成只留存量
